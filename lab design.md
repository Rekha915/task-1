# Proposed lab: Workflow Automation & Approval-Control Lab
 
Derived from my Task 1 workflow: college library borrowing. Rules below must match the final Task 1 report. Edit this file if the Task 1 numbers differ.
 
## Course placement
 
- **Host course:** a new 3-credit lab course in Semester 4, 1-0-4 (replacing the Digital Humanities elective, conditional).
- **Fallback if that swap is not allowed:** run it as the practical component of **Industry Coding Practices** (S4, 2-1-2), with no credit change.
- **Prerequisite knowledge:** Database Management Systems (S3), Object Oriented Programming (S3), Software Engineering & Testing (S2).
## Learning outcomes
 
Students will be able to:
1. Model a manual workflow as states and transitions (request, approve, issue, return, fine).
2. Implement business rules in a database-backed service.
3. Enforce approval control: no state change without an authorised actor and a log entry.
4. Handle failures (duplicate scans, offline staff terminal, mid-update crash) without losing or double-counting records.
5. Measure value against the manual baseline and report it with stated assumptions.
## Synthetic dataset
 
Generated by a script (seeded, reproducible). It contains no real student or library records.
 
| Table | Size (suggested) | Fields |
|---|---|---|
| students | 500 | synthetic ID, name placeholder, email placeholder |
| books | 2,000 | title placeholder, barcode, shelf location, physical/e-book flag |
| loans | 5,000 | student, book, issue date, due date, return date |
| events | generated | scans, extensions, notifications, overrides |
 
Include deliberate edge cases: students at the 2-book limit, overdue books, duplicate scans, an e-book extension, and a missing barcode.

## Rules under test (from Task 1 proposal)
 
- Limit of 2 books per student; returning one allows another.
- Physical book: shelf location shown, staff scan approves issue, fine recorded in the system if late, email after a week.
- E-book: readable for 7 days, extension allowed, no fine.
- Notifications for due dates and payment issues; transaction history visible.
- Fine rate and grace days as stated in the Task 1 report (the current manual process uses Rs 2/day after 3 days).
## Acceptance tests
 
| # | Scenario | Expected result |
|---|---|---|
| 1 | Student with 2 loans requests a third | Rejected with a clear message; no state change |
| 2 | Student returns one book, then requests another | Allowed |
| 3 | Issue without a staff scan | Not completed; loan stays "requested" |
| 4 | Staff scans the same book twice | One loan only (idempotent), second scan logged |
| 5 | Return after the grace period | Fine computed correctly and stored with the loan |
| 6 | Staff overrides a fine | Requires a reason; logged with actor and time |
| 7 | Terminal goes offline mid-issue | On retry, no duplicate or lost loan |
| 8 | E-book extended | New expiry set; no fine created |
| 9 | Notification service fails | Loan unaffected; notification retried and logged |
| 10 | Any state change | An audit entry exists |
 
## How students demonstrate each skill
 
- **Approval control:** tests 3, 6, and 10 pass, and the audit log lists who approved what.
- **Failure recovery:** tests 4, 7, and 9 pass after injected faults.
- **Measured value:** compare manual versus workflow on the same synthetic data. Metrics: steps per transaction, simulated minutes per issue, fine-calculation errors, and records needing manual correction. State all time assumptions. These are synthetic results, not real library measurements.
